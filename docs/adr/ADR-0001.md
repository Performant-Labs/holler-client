# ADR 0001 — Speak Holler protocol v1; answer query locally

**Status:** accepted  
**Issue:** #2  
**Date:** 2026-09-05

## Decision

This body speaks **Holler protocol v1**. The canonical spec is on the server: [`docs/protocol/v1.md`](https://github.com/Performant-Labs/holler-server/blob/main/docs/protocol/v1.md) ([ADR 0009](https://github.com/Performant-Labs/holler-server/issues/10)). Do not fork a client dialect.

This process:

1. Sends OS hostname, features, and **harnesses it can actually drive** in `hello`.
2. Answers `ping` / `pong`.
3. Answers `query` commands (`status`, `caps`, `support`) from **local probes** (PATH, adapter present, session registry) — never by asking a model.
4. Exposes the same answers on CLI: `holler status`, `holler caps`, `holler support <feature>`.

Do not advertise `claude` because it is on the server checklist. Advertise `opencode` only if this box can spawn the v1 adapter (`opencode acp` or the documented fallback).

The client may `query` the server the same way. The server answers as a peer.

## Why

Capability checks have to be boring. “Do you support OpenCode?” is a command with an argument, not a prompt. A wrong `ok: true` is worse than a missing row on the roster.

## Consequences

- Wire story answers `query` as well as `ping`.
- Local `holler status` uses the same document as `query_ok` for `cmd=status`.
